# Production deployment

How to take an application generated by next-feature to production: choosing a deployment target, configuring environment variables, observability, and CI/CD. The details of each piece live in the generator READMEs linked below; this guide shows how they fit together.

| Concern | What you get | Generator / docs |
|---------|--------------|------------------|
| Container image | Multi-stage `Dockerfile` (standalone server, non-root, `HEALTHCHECK`), `.dockerignore`, `compose.yaml` service | [`docker`](./src/generators/misc/docker/README.md) |
| Vercel | `vercel.json` (workspace-root install, `nx build`, Nx output directory, skip unaffected deployments) | [`vercel`](./src/generators/misc/vercel/README.md) |
| CI/CD | GitHub Actions: CI for affected projects, Docker (GHCR) and Vercel deploy workflows, Dependabot | [`cicd`](./src/generators/misc/cicd/README.md) |
| Environment | `lib/config/env.ts` schema, validated when the server starts | [application: environment](./src/generators/project/application/README.md#environment-configuration) |
| Logging | pino server logs (JSON in production), browser log beacon | [application: logging](./src/generators/project/application/README.md#logging) |
| Tracing | OpenTelemetry over OTLP, off until an endpoint is configured | [application: tracing](./src/generators/project/application/README.md#tracing) |
| Health | `/api/health` (liveness), `/api/ready` (readiness) | [application: health checks](./src/generators/project/application/README.md#health-checks) |

Security headers and a Content-Security-Policy aren't generated yet ([#61](https://github.com/dcat23/next-feature/issues/61)); until then, add them in `next.config.js` `headers()` yourself.

## Choosing Docker or Vercel

Both build the same app with `nx build <app>`, so the choice is about where it runs, not how it's built.

| | Docker | Vercel |
|---|--------|--------|
| Runs on | Anything that runs containers: a VM with `docker compose`, Kubernetes, ECS, Cloud Run, Fly.io, ... | Vercel's serverless platform |
| Setup | `nx g next-feature:docker <app>` | `nx g next-feature:vercel <app>`, then a Vercel project with Root Directory = the app |
| Build | In the image (`NEXT_OUTPUT=standalone`), from the workspace root | On Vercel (Git integration) or on GitHub Actions (`cicd --vercel`) |
| Server variables | Runtime: compose `env_file`, `docker run --env-file`, your orchestrator's secrets | Vercel project settings, per environment |
| `NEXT_PUBLIC_*` | Build args (`ARG`/`ENV` in the Dockerfile, `build.args` in compose) | Vercel project settings (inlined at build) |
| Preview deployments | Not included | Per pull request |
| Auth.js URL | Set `NEXTAUTH_URL`/`AUTH_URL` to the public URL and `AUTH_TRUST_HOST=true` (compose does this) | Don't set them: inferred from the request |
| Health checks | Image `HEALTHCHECK` on `/api/health`; point your orchestrator's probes at `/api/health` and `/api/ready` | Not used by Vercel; useful for external uptime monitors |
| Logs and traces | stdout JSON (pino) to your log collector; OTLP to your backend | Vercel's runtime logs; OTLP via env vars or Vercel's OpenTelemetry integration |

Pick **Docker** when you run your own infrastructure, need long-running processes or WebSockets, or want the same artifact in every environment. Pick **Vercel** for zero-ops hosting with preview deployments. One workspace can use both, per app.

## Environment variables

`.env` files are gitignored and never enter a Docker image or a Vercel deployment: every deployed environment sets its variables itself. `.env.example` lists all of them, including optional ones.

### Build time and run time

- **Server variables** are read when the server runs. Change them without rebuilding.
- **`NEXT_PUBLIC_*` variables** are inlined into the JavaScript at build time. Set them where the build runs (Docker build args, Vercel project settings, CI), and rebuild after changing one.

### Validation at startup

When the Node.js server starts, `instrumentation.ts` checks the environment against `lib/config/env.ts`'s schema and exits with code 1, listing every missing or invalid variable:

```
Invalid environment variables (see lib/config/env.ts and .env.example):
  - WEB_API_URL: Required
```

A misconfigured deployment therefore fails its start (and its health check) instead of its first requests. `next build` isn't checked, and neither are `NEXT_PUBLIC_*` variables (they're build-time). `NODE_ENV` must be `development` or `production`. Tighten a schema entry, e.g. `z.string().url()`, to reject bad values too. See [validation at startup](./src/generators/project/application/README.md#validation-at-startup).

### Variable reference

| Variable | Required | When it's read | Set by / notes |
|----------|----------|----------------|----------------|
| `<NAME>_API_URL` | Yes, per API client | Runtime | [`client-config`](./src/generators/misc/client-config/README.md) (also run by the first action): `<APP>_API_URL` for the default client, `<NAME>_API_URL` for named ones. In Docker, `localhost` is the container: use `host.docker.internal` or the compose service name |
| `AUTH_SECRET` | Yes, with `--useAuth` | Runtime | Generated into `.env` for development. Use a different secret per environment (`npx auth secret`); rotating it signs everyone out |
| `NEXTAUTH_URL` / `AUTH_URL` | Outside Vercel | Runtime | The public URL Auth.js builds callbacks from. Compose sets `NEXTAUTH_URL`; on Vercel leave it unset |
| `AUTH_TRUST_HOST` | Outside Vercel | Runtime | `true` behind a proxy or in a container (compose sets it); Vercel trusts the host already |
| `AUTH_GITHUB_ID` / `AUTH_GITHUB_SECRET`, `AUTH_GOOGLE_ID` / `AUTH_GOOGLE_SECRET` | Only for the OAuth providers you keep | Runtime | `.env.example` only. Register the production callback URL with each provider |
| `LOGGING_SERVICE_NAME` | No | Runtime | Overrides the `service` field of log lines (default: the app name) |
| `NEXT_PUBLIC_LOGGING_BEACON_PATH` | No | Build | Only if you move `app/api/log/route.ts` (default `/api/log`) |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | No | Runtime | Turns tracing on, see [Tracing](#tracing) |
| `OTEL_EXPORTER_OTLP_HEADERS`, `OTEL_SERVICE_NAME`, `OTEL_TRACES_SAMPLER(_ARG)` | No | Runtime | Backend credentials, service name override, sampling |
| `PORT` | No | Runtime | Port the server listens on; the Docker image and compose use `3000` |
| `NEXT_OUTPUT` | No | Build | `standalone` switches `next.config.js` to a self-contained server; the Dockerfile sets it |

### Per environment

| Environment | Where variables come from |
|-------------|---------------------------|
| Local development (`nx serve`) | The app's `.env` (and `.env.local`) |
| Local production build (`nx serve <app> --configuration=production`) | The app's `.env`, loaded by Nx |
| Docker (`docker compose up`) | The service's `env_file` (`<app>/.env`) and `environment`; the `docker-run` target without compose passes `--env-file <app>/.env` |
| Kubernetes / ECS / other orchestrators | Your platform's secrets and config maps, as environment variables |
| Vercel | Project settings, per Production / Preview / Development. The `vercel` generator lists the variables to add when it runs |
| GitHub Actions | Repository secrets for the deploy workflows (see [CI/CD](#cicd)); the app's own variables stay with the deployment target |

## Observability

### Logging

Server code logs through pino (`logger` from `lib/config/logging.ts`, or `@next-feature/logging/server`). In production the output is one JSON object per line on stdout, with `service` set to the app name: ship stdout to your log backend (Docker logging driver, a Kubernetes log collector, Vercel's log drains). Browser errors and `GlobalErrorHandler` reports arrive through `/api/log` and go to the same logger. In development, pino-pretty formats the output instead.

### Tracing

Tracing uses OpenTelemetry and is **off until an OTLP endpoint is configured**, so deployments without one export nothing and send no trace headers. Set:

```env
OTEL_EXPORTER_OTLP_ENDPOINT=https://api.honeycomb.io      # or your collector, Grafana Cloud, Datadog, New Relic, Axiom, ...
OTEL_EXPORTER_OTLP_HEADERS=x-honeycomb-team=<api-key>    # the backend's credentials
```

Then a request's trace includes Next.js' own spans, every `ApiClient` call to your backend (with W3C `traceparent` sent along, so the backend's spans join the trace), and the request's log lines carry its `trace_id` and `span_id`, so your backend can link logs and traces. In busy apps, sample with `OTEL_TRACES_SAMPLER=parentbased_traceidratio` and `OTEL_TRACES_SAMPLER_ARG=0.1`. On Vercel, its OpenTelemetry integration also enables it. Details: [application: tracing](./src/generators/project/application/README.md#tracing).

### Health and readiness

| Route | Point at it | Behaviour |
|-------|-------------|-----------|
| `/api/health` | Liveness probes, the Docker `HEALTHCHECK`, uptime monitors | Always `200` while the process serves requests |
| `/api/ready` | Readiness probes, load balancer target health | `503` when a check in `lib/config/health.ts` fails (none by default: add the dependencies the app can't serve without) |

Don't use readiness for liveness: a backend outage would restart healthy instances. Both routes skip the proxy (no auth redirects) and aren't cached. Details: [application: health checks](./src/generators/project/application/README.md#health-checks).

## CI/CD

`nx g next-feature:cicd` writes GitHub Actions workflows (new workspaces get the CI workflow from the preset):

- **CI** (`ci.yml`): `nx affected -t lint test build` on pull requests and the main branch.
- **Docker deploys** (`--docker=<apps>`): after CI passes on the main branch, build the app's image and push it to `ghcr.io/<owner>/<repo>/<app>`, tagged with the commit SHA and `latest`, when the app is affected. Uses `GITHUB_TOKEN`; deploying the image to your runtime (e.g. a Kubernetes rollout, a `docker compose pull` on a VM) is the step you add after the push.
- **Vercel deploys** (`--vercel=<apps>`): production after CI on the main branch, previews for pull requests, built on the runner with the Vercel CLI. It replaces Vercel's Git integration (`vercel.json` sets `git.deploymentEnabled: false`). Needs the repository secrets `VERCEL_TOKEN`, `VERCEL_ORG_ID` and `VERCEL_<APP>_PROJECT_ID`. Without it, Vercel's Git integration builds every push itself, using `vercel.json`'s ignore step to skip unaffected apps.
- **Dependabot** (`--dependencyUpdates=dependabot`): weekly package and GitHub Actions updates, except Nx (update it with `nx migrate latest`).

Deploy workflows only run for apps a change affects, including changes to the feature libraries they import. Details: [`cicd`](./src/generators/misc/cicd/README.md).

## Checklist

- [ ] Every required variable is set in each environment; the server starts (it exits naming any missing one)
- [ ] `AUTH_SECRET` differs per environment; OAuth providers have the production callback URLs
- [ ] Outside Vercel: `NEXTAUTH_URL`/`AUTH_URL` is the public URL and `AUTH_TRUST_HOST=true`
- [ ] `NEXT_PUBLIC_*` values are set where the build runs
- [ ] Orchestrator probes: liveness on `/api/health`, readiness on `/api/ready`, with readiness checks for the app's critical dependencies
- [ ] Logs are collected from stdout; tracing has an OTLP endpoint and credentials if you want traces
- [ ] CI passes on the main branch before deploys run; deploy secrets are set
- [ ] Security headers and a CSP, until generated ([#61](https://github.com/dcat23/next-feature/issues/61))
